# Document Template save hangs / times out on the VPS (WAF blocking SQL)

**Symptom:** On the VPS (production), saving a **Document Template** that contains a
large/"heavy" SQL query in one of its data sources **hangs and then 504s** (or shows a
403 / block page). The same template saves instantly on localhost / dev.

**Applies to:** the Document Generator (`avinashgroup_app.custom_code.document_generator`),
DocType **Document Template** and its child **Document Template Data Source**.

---

## Root cause — it is NOT the SQL, and NOT Frappe

Saving a Document Template does **not** execute the data-source SQL. The save path only
runs `DocumentTemplate.validate()`:

- `validate_companies()` — de-dupes the company list
- `validate_jinja()` — dry-renders body/header/footer against an **empty stub context**
  (`providers.stub_context()`), so loops run zero times and no query runs

See `avinashgroup_app/avinash_group_app/doctype/document_template/document_template.py`
(the `validate` method) and `custom_code/document_generator/providers.py`
(`stub_context`, `_run_sql_source`). The data-source SQL only runs later, at **generate /
preview** time (`instantiate_document` / `preview_template` in `api.py`).

So saving is just a fast DB text-write. If it hangs for ~120s and 504s, something is
intercepting the HTTP request **before it reaches Frappe**. The only thing unusual about
this request is that its body contains raw SQL
(`SELECT … tabGL Entry … CASE … UNION …`). A **WAF reads that as a SQL-injection attack**
and blocks or tarpits the request.

The save request goes to:

```
POST /api/method/frappe.desk.form.save.savedocs
```

with the whole document (including the SQL) in the body.

### Confirmation that the queries are not the problem
The Balance Confirmation data sources are per-party, single-table aggregations. On the
`avinas1` DB the busiest customer's `balances` query (against `tabGL Entry`, 5k+ rows for
that party) runs in **~0.16s** using the `party_type_party_index`. GL Entry already has
all the needed indexes. The SQL is fine; the request layer is the issue.

---

## Step 1 — Confirm it is the proxy/WAF (~2 min)

Reproduce the save while tailing the logs on the VPS:

```bash
sudo tail -f /var/log/nginx/error.log
# ModSecurity audit log (path varies):
sudo tail -f /var/log/modsec_audit.log 2>/dev/null || \
  sudo tail -f /var/log/nginx/modsec_audit.log 2>/dev/null
```

Save the template in the browser. Look for a line like:

```
ModSecurity: Access denied ... [id "942100"]   # 942xxx = OWASP SQL-injection rules
```

Also open **DevTools → Network**, find the `savedocs` request, and note the status:

- `403` / block page  → **WAF confirmed**
- `504` after ~120s   → timeout / tarpit (still usually a WAF buffering + rule eval, or a
  worker timeout)

Identify what is in front of Frappe:

```bash
nginx -V 2>&1 | grep -io modsecurity          # ModSecurity compiled in?
grep -ril modsecurity /etc/nginx/             # ModSecurity enabled in config?
curl -sI https://YOUR-DOMAIN | grep -i 'cf-ray\|server'   # cf-ray => Cloudflare in front
```

---

## Step 2 — Fix: whitelist the Frappe save endpoint

Only the save endpoint needs the SQLi rules relaxed — keep the WAF on everywhere else.

### If ModSecurity (nginx)
In the site's nginx server block, disable the OWASP SQLi ruleset for the save endpoint
only:

```nginx
location = /api/method/frappe.desk.form.save.savedocs {
    modsecurity_rules 'SecRuleRemoveById 942100-942999';
    # keep your existing proxy_pass to the Frappe upstream:
    proxy_pass http://frappe-bench-frappe;   # match your bench upstream name
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> Frappe's nginx config is generated by `bench setup nginx`. Add this via a custom include
> (or re-apply after regenerating) so it survives `bench setup nginx`.

### If Cloudflare
Dashboard → **Security → WAF → Custom rules** (or Managed Rules exceptions) → add a
**Skip** rule:

- When: `URI Path` contains `/api/method/frappe.desk.form.save.savedocs`
- Action: **Skip** → skip **Managed Rules** (the SQLi / OWASP set)

To confirm the cause first: temporarily set the zone WAF to **"Essentially Off"**, retry
the save, then re-enable with the skip rule in place.

### If it is actually a timeout (you saw 504, not a block)
Raise the request timeout:

```bash
bench config http-timeout 300
bench setup nginx && bench setup supervisor
sudo supervisorctl reload && sudo systemctl reload nginx
```

---

## Step 3 — Fallback (only if the WAF cannot be changed)

If the WAF is managed by a third party and cannot be adjusted, make the SQL not look like
SQL in transit: store each data-source `query` **base64-encoded** and decode it in
`_run_sql_source()` (`custom_code/document_generator/providers.py`). This is a small code
change and keeps working, but adjusting the WAF (Step 2) is the correct fix and keeps the
SQL readable in the DocType. Prefer Step 2 whenever possible.

---

## Quick reference

| Layer | Save runs SQL? | Cause of hang | Fix |
|-------|----------------|---------------|-----|
| Frappe `validate()` | No (Jinja stub only) | — | not the cause |
| Data-source SQL | Only at generate/preview | slow query on big prod data | `bench config http-timeout`, indexes |
| **Proxy / WAF** | n/a | **SQL in POST body flagged as injection** | **whitelist `savedocs` endpoint** |

**Endpoint to whitelist:** `/api/method/frappe.desk.form.save.savedocs`
**OWASP SQLi rule range:** `942100`–`942999`
